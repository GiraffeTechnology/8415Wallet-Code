# Native wallet-control login

The native API uses the existing account/chain registration and the same public authentication protocol as the UI. It does not require an injected browser provider, a username lookup, or transaction-signing permission.

`createNativeWalletLoginSigner` is exported by the authentication service module. Application composition passes the existing custody account capability (`address`, `signMessage`) and its exact origin, tenant, account and chain. No private key, seed, key file path, credential import or custody migration is an API input. The account capability remains inside its original custody process. The returned capability exposes only `signLoginChallenge`; it cannot sign arbitrary messages, typed data or transactions.

`createNativeWalletLogin({client, signer}).authenticate()` calls the real `bootstrap`, `challenge`, and `proof` endpoints through the existing authenticated client. It retains cookie/CSRF state inside that client and returns the server-issued session. It does not probe capabilities or synthesize a session. Logout revokes the session through the same service.

Before signing, the signer reconstructs the exact two-minute login message and tenant/purpose/request resources. It checks account, chain, origin, tenant, freshness and one-use request identity. A changed purpose or arbitrary message is refused. An attempted signing call is never retried automatically after an error or unknown outcome. Signature recovery must match the original account. Cancellation or account change during signing prevents proof dispatch. These checks do not request a fresh human signature for an already authorized Agent.

A login proof grants no asset operation, task, fee budget or transaction authority. Existing grant validation, saved owner settings, revocation and UNKNOWN reconciliation remain separate. Transaction sign-only adapters cannot substitute for a login-message signer.

The implementation includes isolated real HTTP protocol tests with a synthetic custody account. Production readiness additionally requires consuming the exported capability inside the existing custody process and independently verifying the real account/chain login. Source tests alone do not establish that deployed binding.

## Concrete local custody and native HTTP composition

`createNativeKeystoreWalletLogin` implements local encrypted-keystore loading and decryption itself; its caller does not have to implement `signMessage`. Fixed installation composition supplies the **existing** encrypted JSON keystore and **existing** local unlock credential references for the original account. Both must be regular, owner-only Linux files without symlink or hardlink aliases. The implementation verifies the decrypted account against the selected account and keeps the wallet object inside the original custody process. It never creates a key, imports one through HTTP, rewrites a keystore, or transfers it to another host. Other original custody formats need their own original in-process adapter; the product does not reinterpret a store-encryption key as a wallet key.

`createNativeWalletAuthClient` implements the native cookie/CSRF transport, rather than assuming Node fetch provides a browser cookie jar. It refuses redirects and cross-origin responses, sends Origin, retains only the exact tenant's secure HttpOnly Strict cookies and never logs or returns those cookies. The returned authenticated client can be used by the original consumer for separately authorized API requests; login itself grants no business authority.

Actual installation must bind the existing local keystore/credential references inside their current custody host. Missing references limit that installation action; they are not a request for the user to provide a never-implemented signing helper. Do not point this API at unrelated keys or manufacture replacement credentials.

`createNativeRawKeyWalletLogin` also preserves an existing local 32-byte hexadecimal key-file custody format. It validates the same original account without converting it into a new keystore. A descriptor, inode/device and post-read leaf check prevent file substitution; buffers are cleared after loading. Windows composition retains its original ACL verifier and file identity checks. This compatibility API does not grant permission to execute tests on a prohibited host or move a key. Real installation uses the original owner-approved custody reference, not a newly created fixture file.

## Original custody process wire

`createNativeLoginCustodyBridge(binding)` loads the original raw-key account internally and exposes one `handle` operation. Its input is exactly `{schema: "8415wallet-native-login-request/1", challenge}`; its output is exactly `{schema: "8415wallet-native-login-proof/1", requestId, signature}`. The original consumer checks requestId against its outstanding challenge and supplies only the signature to the real proof endpoint. No key path, account object, cookie or session crosses this wire. `runNativeLoginCustodyRequest` supports a bounded JSON request/output inside an already authorized local process. The binding and original ACL verifier come from installation composition; they cannot be supplied in the request. No public signing daemon or guessed network route is introduced.

An installation retaining the original bounded directory-based raw-key loader may use `keyDirectory` in the custody bridge binding instead of `keyFile`. The product scans only that original local directory, with the retained depth/file-count bounds, ACL or owner-mode checks and descriptor/inode/leaf identity checks. It selects only the exact configured account and refuses duplicate references. The located path and account object remain inside the custody process; no caller-supplied directory is accepted in the login request. No keystore conversion or user-provided signing helper is required.

The proof-only custody bridge also accepts the existing encrypted-keystore composition: installation-owned `keystoreFile` and `unlockCredentialFile`, with the same owner-only Linux file checks and exact original account verification. These references are mutually exclusive with `keyFile` and `keyDirectory`. This branch constructs only the bounded signer; it does not create an HTTP client or dispatch a proof. Input/output and no-automatic-retry rules are unchanged. It consumes already-present custody inputs and does not implement cross-host import or a human secret-entry mechanism.

The generic `server/native-login-stdio.mjs` exports `createNativeLoginStdioHandler` and `runNativeLoginStdio`. Installation supplies fixed account/context bindings and authenticates the caller. The wrapper accepts one EOF-delimited UTF-8 JSON request, at most 16384 bytes with a bounded read deadline, rejects duplicate keys at every level, then validates the exact challenge, allowlisted account/context, purpose and TTL before constructing custody. It accepts no commands, paths or configuration from stdin. Only a matching proof is written to the supplied output; errors produce no proof. This transport does not establish caller authorization, create keys, move custody, or grant transaction access.

`createNativeLoginProofSigner` adapts the same fixed exchange capability to the existing native client signer interface. It validates the challenge before exchange, sends only the bounded request, verifies exact proof schema/request identity and the recovered original account, then returns only `{signature}`. Cancellation, expiry, duplicate fields, extra outputs and unknown exchange outcomes fail without automatic retry. `createNativeWalletLogin` and `createNativeWalletAuthClient` remain the existing HTTP/session composition; no second login protocol or embedded SSH command is introduced.
